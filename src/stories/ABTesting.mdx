# A/B Testing

Attach test cells so the agent's tracking events can be attributed to the cell a shopper is in.

## What you need

Your own A/B system decides which cell each shopper is in. The library does not assign cells, read
them from the page, or persist them — you resolve the cell and pass it in.

## Setting it up

Pass `testCells` alongside your API key:

```jsx
<CioAsa
  apiKey='YOUR_API_KEY'
  testCells={{ constructorio: window.cnstrc.testCell }}
/>
```

Every event the agent sends then carries an `ef-<testName>` parameter per cell.

## Several tests at once

`testCells` is a `{ [testName]: cellName }` map, and the keys are your own test names, not values
Constructor defines. A shopper in several concurrent tests carries every cell:

```jsx
testCells={{ constructorio: 'variant_a', checkout_flow: 'b' }}
```


## If you supply your own `cioClient`

A client you construct owns its own options, so set the cells there and the library will leave them
alone:

```jsx
const cioClient = new ConstructorIOClient({
  apiKey: 'YOUR_API_KEY',
  sendTrackingEvents: true,
  testCells: { constructorio: window.cnstrc.testCell },
});

<CioAsa cioClient={cioClient} />
```

The `testCells` prop is ignored in this case and logs a warning, so the value is never dropped
without telling you.

## Checking that it works

Open the network tab and filter on `cnstrc`. The agent's tracking requests should carry an
`ef-<testName>=<cellName>` query parameter for each cell you passed.
