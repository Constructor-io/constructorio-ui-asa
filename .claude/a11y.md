# Accessibility review rules

Target: **WCAG 2.2 AA**.

## What this file is for

Two automated layers already run on every PR, and they are the merge gate:

1. `eslint-plugin-jsx-a11y` (`npm run lint`) — static errors visible in the JSX source.
2. `axe-core` against Storybook stories in real Chromium (`npm run test-storybook:ci`) — contrast, accessible names on the rendered DOM, ARIA validity, duplicate ids, target size.

**Do not restate what those two catch.** They are deterministic and they already failed the build if they found something. Your job is the half they cannot do: judging whether markup that *passes* the automated checks is actually usable. Everything below is a judgement call that requires reading the code, not running a tool.

## What to review

### Accessible-name *quality*

axe only checks a name exists. Check whether it is any good.

- Does `aria-label` describe the action, or does it restate the element (`aria-label='button'`, `aria-label='icon'`)?
- **Label in Name (2.5.3)**: if a control has visible text, the accessible name must contain that text. `<button aria-label='Submit'>Send</button>` is a failure — a voice-control user saying "click Send" cannot activate it.
- Does `alt` describe the image's purpose, or repeat a filename / the word "image"?
- Is the name stable, or does it interpolate something that can be empty at runtime? An `aria-label={someProp}` that resolves to `''` is a critical failure that only shows up for certain prop combinations. Check every branch.

### Decorative vs meaningful

- Inline SVG sitting next to visible text is decorative → needs `aria-hidden='true'` and `focusable='false'`.
- An icon-only control needs a real name, and its icon still needs `aria-hidden`.
- Flag `aria-hidden` on anything that is focusable — it creates an element a keyboard can reach but a screen reader cannot announce.

### State, not just role

- Toggles need `aria-pressed`; disclosures need `aria-expanded`; selected nav items need `aria-current`. A button whose *appearance* changes on click but whose *markup* does not is invisible to assistive technology.
- **1.4.1**: any state conveyed only by colour (icon fill, border tint) must also be conveyed non-visually.

### Focus intent

- Anything that opens (modal, drawer, popover) must move focus in, and **return focus to the trigger on close**. Check the close path, the Esc path, and the backdrop-click path — they often diverge.
- Native `<dialog>.showModal()` already traps focus. A hand-rolled focus trap on top of it is a bug, not a feature.
- Watch for elements hidden with a CSS class (`.invisible`, `opacity: 0`) rather than `display`/`visibility`/`hidden` — they stay in the tab order while being invisible.

### Live regions

- Errors that appear asynchronously need `role='alert'`; async content needs `aria-live` / `aria-busy`.
- But a live region on a frequently re-rendering element is noise, not accessibility. Flag over-application too.

### Custom widgets

- `onClick` on a non-interactive element must also be keyboard-operable, or be a real `<button>`.
- Carousels, menus, tabs, comboboxes: check against the APG pattern for the expected keys, not just for "can you Tab to it".

### `dangerouslySetInnerHTML`

Neither the linter nor axe-in-a-story sees inside injected markup reliably, and here it is often LLM-generated. Check heading hierarchy (no level skips), link text (no bare "click here"), and that lists are real lists.

### i18n

An `aria-label` hardcoded in English bypasses the `translate()` system and is an accessibility bug in every other locale. All user-facing strings, including accessible names and live-region text, go through `translate()` with the key added to `defaultTranslations` and the `Translations` type.

### Regression guard — the most important item

**Flag any diff that removes or weakens an existing accessibility affordance**: a deleted `aria-*` attribute, a semantic element replaced by a `div`, a removed `tabIndex`, a `role` dropped during a refactor. This is the single most common way accessibility silently rots, and it is easy to miss when reviewing a large refactor for its stated purpose.

## Severity

Report accessibility findings as `**Important Issue**` or `**Suggestion**`. **Never** `**Critical Issue**` — the automated gate is lint + axe; this layer is advisory and must not read as a merge blocker.

If a finding is something lint or axe would already have caught, do not report it: the build would have been red.
